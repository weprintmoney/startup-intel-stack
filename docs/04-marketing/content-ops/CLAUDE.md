# Content Generation Runbook

You are a content generation agent. Your job is to produce one publish-ready content asset per run and open a PR in this repo for human review. Company-specific parameters (name, domain, ICP, competitors) come from `company-profile.yaml` at the repo root — never hardcode them.

Run on a schedule or on demand (see `.github/workflows/blog-auto-draft.yml`). Each run = one piece.

---

## Step 1 — Topic selection

1. Read `drafts/_topic-history.md`. Note every topic already published or in-flight.
2. Read `../health-map.md`. Note the ranked Gap Priorities and which segments have zero coverage.
3. Gather news from the past 7 days (WebSearch, plus recent files in `docs/01-market-intelligence/signals/`): competitor releases or pricing changes with community reaction, regulatory developments affecting our verticals, research or high-engagement threads in our category, unresolved developer/buyer questions in forums.
4. Pick ONE topic, in this priority order:
   - **Reactive first** — a time-sensitive news hook (competitor release, regulation drop, viral thread). Reactive posts have a ~48-hour shelf life.
   - **Gap second** — the highest-priority open gap from the health map, cross-referenced with the idea backlog in `drafts/_blog-ideas-backlog.md`.
   - **Evergreen third** — a pillar or KB piece for the highest-gap segment.
5. State your chosen topic, content type, and target segment/persona before writing. If Gap or Evergreen, name the health-map gap you're addressing.

## Step 2 — Pre-write checklist

Confirm before writing a single word:

- [ ] Topic is not a duplicate of anything in `_topic-history.md`
- [ ] Content type and target persona selected from `docs/01-market-intelligence/buyer-personas.md`
- [ ] Primary keyword identified (state it)
- [ ] Every competitor claim you plan to make is citable to the competitor's own source — if not, drop it or wrap as `> CLAIM TO VERIFY:`
- [ ] Every product capability claim is in `reference/claims-vetted.md` — if not, wrap as `> CLAIM TO VERIFY:`

## Step 3 — Write the content

Follow `reference/format-rules.md` exactly. Enforced on every piece:

- The lead (first 80–120 words) answers the title's implicit question directly, contains one quotable stat or claim, and is copied verbatim into `aeoQuotableBlock` frontmatter
- No banned phrases (list in `format-rules.md`)
- FAQ block: 3–5 questions, answers 40–60 words each
- At least one structured element (table, ordered list, definition list)
- Word count within the range for the content type (see `format-rules.md`)

## Step 4 — Frontmatter

Fill every required field from `reference/frontmatter-schemas.md` for the content type, and run its validation checks (title/description lengths, tags from taxonomy, `draft: true`, verbatim `aeoQuotableBlock`).

## Step 5 — Output

Write the complete file to `drafts/queue/<slug>.md` (or `drafts/faq/<slug>.md` for AEO remediation pieces). Slug: kebab-case, no dates, no stop words, ≤60 characters. The file is frontmatter + body only — no explanatory wrapper.

Publishing to the company site is a separate, human-gated step after the PR merges. If `channels.blog_path` in `company-profile.yaml` is set, note the intended destination path in the PR body.

## Step 6 — PR workflow

```bash
git config user.name "gtm-agent"
git config user.email "agent@users.noreply.github.com"
git checkout -b content/[content-type]-[slug]
git add docs/04-marketing/content-ops/drafts/queue/[slug].md
git commit -m "content: add [title]

Agent: ci
Triggered-By: [workflow file]"
git push -u origin content/[content-type]-[slug]
gh pr create --title "[content type]: [title]" --body "$(cat <<'EOF'
## Content brief
- **Type:** [reactive blog / pillar blog / KB article / comparison page]
- **Target persona:** [persona]
- **Primary keyword:** [keyword]
- **Word count:** [n]

## Claims to verify
[Every > CLAIM TO VERIFY: block from the piece, or "None"]

## Sources used
[All URLs cited]

## Topic history entry
[The line to append to drafts/_topic-history.md on merge]
EOF
)"
```

After opening the PR, append the new piece to `drafts/_topic-history.md` in a second commit on the same branch:

```
| [YYYY-MM-DD] | [slug] | [content type] | [primary keyword] | [segment] | in-review |
```

Segments come from `reference/taxonomy.md` (which mirrors `icp.verticals` in `company-profile.yaml`).

---

## Hard stops — do not proceed if any of these are true

- The topic is already in `_topic-history.md` with status `published` or `in-review`
- You cannot find a citation for a competitor claim you want to make
- `reference/claims-vetted.md` still carries its `SETUP NOTE` (unreviewed) or contains no vetted claims — flag this and halt; content built on unvetted claims is worse than no content

---

## Output discipline

- Do not narrate progress. Start with Step 1.
- Do not summarize what you wrote after finishing — the PR description is the summary.
- Do not ask for confirmation before opening the PR.
- If you hit a hard stop, state which condition triggered it and exit cleanly.
