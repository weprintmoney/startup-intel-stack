# Prompt 1: The checked docs repo

Every agent you add later will read your docs and trust them. This prompt makes the docs checkable before anything depends on them. Each doc says who owns it, what state it's in and when someone last confirmed it. An approved doc also says who approved it and what it's based on. One script fails the build when any of that is missing.

The reasons for each choice are in the [chapter overview](README.md).

## What you'll have

- A rule, in `docs/README.md`, for the fields every doc starts with.
- `scripts/check_docs.py`, which checks the fields, the links between docs, the sources on approved docs, hidden characters, and that the index is current.
- `docs/INDEX.md`, generated by the script: one line per doc with its description.
- A CI job that runs the script on every pull request and every push to the default branch.
- A weekly job that keeps one issue listing the docs nobody has confirmed in 180 days.

## Before you start

Open Claude Code in the repo. The script uses only the Python standard library. The weekly issue needs GitHub; everything else works on any CI system.

## The prompt

```text
Make this repo's docs folder a checked single source of truth. Work in this repo and fit in with what exists. Don't move or rename existing files. I am the only person working on this repo.

The principle for the whole build: a rule that matters is a check that fails, not a sentence asking people to behave. Every format rule below is enforced by one script that runs in CI on every change, whoever or whatever made it.

First look at what exists: a docs/ folder, a README, a CI setup, a test runner.

Build these, in this order:

1. The rule, written in docs/README.md. Every Markdown file under docs/ except README.md files and the generated docs/INDEX.md starts with YAML frontmatter:
   - title
   - description (one line; this is what a reader or an assistant scans to decide whether to open the file)
   - owner (one person's handle, or "unassigned")
   - status: draft, approved or archived. Nothing else.
   - last_reviewed (YYYY-MM-DD: the last day someone re-read the whole doc and confirmed it)
   - When status is approved, two more fields are required: approved_by (the handle of the person who approved it) and sources (a list; each entry is a path in this repo or an https URL that supports what the doc says). A doc with no source is not approved. sources is allowed, and encouraged, on a doc of any status.
   Also state three writing rules there: one home per fact (link to it, don't copy it); mark anything not checked as "(unverified)"; delete or archive a doc that is no longer true.

2. scripts/check_docs.py, standard library only. With no arguments it checks everything, prints "path: reason" (or "path:line: reason") for each problem, and exits 1 if there are any:
   - a doc with no frontmatter, a missing or empty field, a field not listed above, a status outside the three, a date that isn't a real YYYY-MM-DD date, or a last_reviewed date in the future
   - an approved doc with an empty approved_by or no sources; a source that is a repo path and doesn't exist; a source that is neither an existing repo path nor an https URL; a doc that lists itself as its source
   - a relative Markdown link in any doc or README under docs/ that points at a file that doesn't exist or at a path outside the repo (ignore http links, mailto links and in-page anchors; ignore links inside fenced code blocks and inline code). Match file names exactly, including capitals, so the result is the same on every operating system.
   - hidden characters in any file under docs/ or .claude/, and in CLAUDE.md and AGENTS.md if present: zero-width characters, bidirectional control characters and Unicode tag characters. Print the code point, for example U+200B. These can hide instructions from a human reviewer.
   - docs/INDEX.md missing or different from what the script would generate
   Other behaviour:
   - "--write-index" writes docs/INDEX.md: a heading per folder, then one line per doc in that folder: "- [title](relative path): description (status, last_reviewed)". Folders and docs in order of file path. Archived docs are left out, with one closing line saying how many were left out. The file starts with a comment saying it is generated and must not be edited by hand. It refuses to write while any doc has broken frontmatter.
   - a warning on stderr, without failing, for each doc that is not archived and whose last_reviewed is more than 180 days old
   - "--stale" prints only those docs as a Markdown list, oldest first, with the owner and the age in days, or the single line "No stale docs." It always exits 0. "--days N" changes the threshold.
   - "--today YYYY-MM-DD" fixes the date and "--root PATH" points at another tree, both for tests.
   - Exit 2 with a clear message if docs/ doesn't exist.
   Parse the frontmatter yourself; don't add a YAML dependency. Support plain "key: value" lines, quoted values, inline lists like [a, b] and dash lists.

3. Tests that need no network: one passing fixture tree, and one failing fixture for each rule in step 2. Build the fixtures in temporary folders so no broken doc is committed. Test "--stale" and the 180-day warning with a fixed "--today". Test that "--write-index" followed by a check passes, and that editing INDEX.md by hand then fails. Use the test runner this repo already has, or plain unittest.

4. CI on every pull request and every push to the default branch: run the tests, then the script. Do not limit the job to certain paths, because a check that is skipped can't be made a required check. Read-only permissions. Use the CI system this repo already uses; if none, GitHub Actions.

5. A second, weekly scheduled job, plus a manual trigger: run "--stale" and write the result to the job summary. Keep exactly one open issue labelled "docs-stale" in step with it: create it if there are stale docs and none is open, replace its body if one is open, close it if nothing is stale. Put that logic in a small script of its own so it can be tested without GitHub. This job, and only this job, may write issues. It must not be able to write code.

6. Bring existing docs into line. Add frontmatter to any doc under docs/ that lacks it: status "draft", owner "unassigned", title from the first heading, a one-line description from the content. Set last_reviewed to the date of the file's last commit, not today: adding frontmatter is not a review. Use today only for a file with no history. Never set a doc to approved yourself and never fill in approved_by; only a person does that. If a doc already has frontmatter with other fields or other status values, don't change it: list those docs, say what would fail, and ask me. If there are no docs yet, write one short real doc, docs/how-we-keep-docs.md, describing the rule. Then run "--write-index".

Finish by running the tests and then the script, and show me both outputs. Then tell me four things:
- every doc you marked "unassigned"
- the exact repository settings I should turn on so that the default branch accepts changes only through a pull request with this check passing. I work alone, so don't require an approving review. Tell me; don't change repository settings yourself.
- anything you noticed in the docs that looks wrong or is stated in two places
- anything in this prompt you could not do, or did differently, and why
```

## What you should see

A passing test run, a clean run of `check_docs.py`, a list of docs that need an owner, the repository settings to turn on, and a short list of content problems it noticed but left alone.

If some of your docs already have frontmatter that doesn't fit, the check will fail at the end and the assistant will ask you what to do with them. Answer, and ask it to regenerate the index.

Docs that haven't changed in six months will show as stale straight away. That's accurate: nobody has confirmed them.

## Check it yourself

Each step breaks one thing. Undo each before the next.

1. Delete the `owner:` line from any doc and run `python3 scripts/check_docs.py`. It should name the file and say `owner` is missing.
2. Add a line to the end of `docs/INDEX.md`. The check should say the index differs from the generated one.
3. Add the line `See [this](missing.md).` to a doc, outside any code block. The check should give the file and line.
4. Change a doc's `status` to `approved`. The check should say it has no `approved_by` and no sources.
5. Run `python3 scripts/check_docs.py --stale --today 2030-01-01`. Every doc that isn't archived should be listed with its age.

If any step passes silently, tell the assistant what you did and ask it to fix the script and add a test for that case.

## Then turn on the settings

Until the repository requires the check, everything here is advisory: a failing change can still be merged.

Open one pull request so the check runs once. Then, on GitHub, protect the default branch: require a pull request, require the docs check to pass, and don't allow anyone to bypass the rule, yourself included. GitHub's guide is [About protected branches](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-protected-branches/about-protected-branches). Use the assistant's list as a starting point and check it against that page, since it was written from memory. On a private repository, whether you can require checks depends on your plan.

## What this doesn't do

- It can't tell whether a doc is true. A date shows that someone confirmed the doc, not that they were right.
- It checks that `approved_by` holds a handle, not who typed it. Your review of the pull request is what makes approval real.
- It checks that a source exists, not that the source supports the doc.
- `README.md` files under `docs/` are exempt from the fields, so don't keep facts in them.
- A pull request can change the script it is judged by. Read any diff to `scripts/`, the tests and the CI configuration yourself.
- The hidden-character scan will flag some emoji and can't see HTML comments, which are also invisible in a rendered page.

## Tested

2026-11-14, twice, each time in a small fictional company repo by an assistant given only the prompt. The prompt above is the one used in the second run.

**Second run.** The repo held a README, one source file, three docs with no frontmatter and one doc with frontmatter that didn't fit the rule. Its only commit was dated eight months earlier.

- It built the rule, the script, 58 passing tests and both workflows.
- It gave the three bare docs the date of their last commit, not the day of the run, so all three showed as stale at once. That is the intended result.
- It left the fourth doc alone, reported what would fail, and asked what to do. Until that was answered the check failed and no index was written. Once the doc was fixed by hand, the index was generated and the check passed.
- All five checks above were then run by hand, and each failed as described.
- It reported content problems without changing them: one fact stated in two places, a setup doc that didn't match the code, and two figures with nothing in the repo to support them.
- It listed branch settings with no required approval and no bypass. The list was written from memory and not checked against GitHub.

**First run**, with an earlier version of the prompt: the build passed the same checks, and a zero-width space added to a doc was caught with the file, line and code point. That version dated every doc as reviewed on the day of the run and proposed a required approval a solo operator can't give. Both were corrected in the prompt, and the second run confirms the corrections.

**Not tested in either run:** neither workflow has run on a CI service, and the issue-keeping logic was tested against a stand-in, not GitHub.
